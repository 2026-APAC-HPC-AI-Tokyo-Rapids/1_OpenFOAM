# Gadiの運用

Gadiでは、小ファイルを大量に置く処理と、長く保存する大きなファイルを分けます。

- ログインノード上の実行機の`/tmp`には、ソースの展開先、ビルド作業領域、ccacheの一時ファイルを置きます。
- ログインノード上の実行機の`/dev/shm/ccache-${USER}`には、10 GBを上限とする一次ccacheを置きます。
- `/scratch/hb15/tk7779/openfoam/gadi`には、圧縮したソース、検証済み公式メッシュ、ビルド成果物、共有ccache、領域分割済みケースの圧縮ファイル、実行記録と回収対象だけを置きます。
- PBS計算ノードでは、OpenFOAM実行環境と完全な領域分割済みケースを各ノードの`$PBS_JOBFS`へ展開します。展開した実行環境、非分割メッシュ、`processor*`ディレクトリは`/scratch`へ置きません。
- 玄界の成果物やキャッシュをGadiで再利用しません。

Gadiの`/tmp`と`/dev/shm`はログインノード上の約126 GiBのtmpfsです。`/dev/shm`は`noexec`なので実行ファイルを生成するビルドや計算には使いませんが、ccacheの保存物には使えます。ビルド終了時に`/tmp`の展開物、中間生成物、ccacheの一時ファイルを削除し、`/dev/shm`の一次ccacheはログインノードが保持する間だけ再利用します。

OpenFOAM実行環境1件の展開には約35,000--37,000 inodeを使います。2026年8月17日に3実行を同時に配備したところ、`hb15`のinode上限212,100へ同時に到達し、3件とも`tar: Disk quota exceeded`で失敗しました（Actions `32002206618`、`32002206644`、`32002207026`）。失敗した3件の展開物を削除するとinode使用量は210,900から121,823へ戻りました。ビルド成果物のSHA-256ごとに実行環境を共有展開する暫定策でも、領域分割済みケースを実行ごとに共有領域へコピーすると同じinode制約に当たりました。このため、共有展開キャッシュと実行固有のケース複製は廃止します。

ケース準備PBSだけが`$PBS_JOBFS`へ実行環境、公式メッシュ、全`processor*`ディレクトリを展開し、完全な領域分割済みケースを単一の`case.tar.zst`として、容量とSHA-256を記した管理情報とともに`case-archives`へ保存します。通常実行PBSは`$PBS_NODEFILE`から割当ホストを明示し、各ノードに同じ実行環境の圧縮ファイルと完全なケースの圧縮ファイルを展開します。各ランクは同じノードの`$PBS_JOBFS`にある自分の`processor*`ディレクトリを読み書きします。複数ノード時だけOpenFOAMの補助処理とソルバーへ`-hostRoots`を渡し、各ノードの先頭ランクを`-ioRanks`へ指定します。動的コンパイルライブラリなどルート間で配布するファイルは、1ノードにつき1ランクだけが書き込みます。1ノードでは全ランクが同じジョブローカルファイルシステムを見るため、分散ルートを有効にしません。圧縮ファイルの検証と展開はソルバー計測区間の前に完了させ、通常計測値へ含めません。

`jobfs`要求は各ノード100 GBです。PBSの`jobfs`はジョブ全体への要求値であり複数ノードへ分配されるため、実行投入では`nodes * 100 GB`を指定します。ランクごとの実行管理情報の参照と配置情報の生成も各ノードの`$PBS_JOBFS`で行い、solver終了後に各ノード1プロセスだけが小さな配置情報JSONを共有実行ディレクトリへ回収します。`/scratch`上の実行ディレクトリへ残すのは、solverログ、公式判定、計測値の断片、ハードウェアと配置の記録、プロファイル出力などの回収対象だけです。

32 KiBのファイル4096個を作成した実測では、`/dev/shm`と`/tmp`が約0.08秒、`/scratch`が約5秒でした。一次ccacheを`/dev/shm`、別のlogin nodeからも使う共有ccacheを`/scratch/hb15/tk7779/openfoam/gadi/ccache`へ置きます。`~/.config/ccache/ccache.conf`で一次ccacheを`max_size = 10GB`とし、共有ccacheはビルド後に`ccache --trim-dir`で10 GBまで整理します。`max_size`は共有ccacheに適用されず、容量による整理ではinode数も保証されないため、最初の実ビルド後に共有ccacheの実ファイル数も確認します。

ビルドはログインノード上の実行機で16並列にします。24物理コアのソケット2基に合わせた48並列では、公式v2512のライブラリ群をIntel `icpx`でビルドした際に複数のコンパイラ処理が同時に強制終了されました（Actions実行`31990408500`、2026年8月17日）。CPU数ではなく実測したメモリ制約を採用し、GCC導入時にも完走実績のある16並列を使います。環境変数`OMP_NUM_THREADS=1`の影響で`nproc`は1を返すため、並列数の決定には使いません。

計算ノードから外部ネットワークへは接続できません。実行中の計測値断片は`/scratch`上の実行ディレクトリへ記録し、PBS終了後にログインノード上の実行機から一度だけ送信します。計算ノードへBigQueryの資格情報を環境変数で渡しません。

GitHub Actionsの実行機は、版ごとに用意した`shared/<version>/externals`を共有します。共有物の初回作成と版の切り替えは運用者が手作業で行い、ワークフローや起動スクリプトから作成・更新しません。各実行機の`bin`、認証情報、診断記録、作業領域は共有しません。

PBSの投入先は課題`hb15`の`normalsr`です。投入、待機、終了確認、資源指定はGadi用のスクリプトに置き、PJM用の処理と共通化しません。

ビルドと実行には`intel-compiler-llvm/2025.1.1`と`intel-mpi/2021.15.0`を使います。これは玄界と同じIntel C++ 2025.1.1、Intel MPI 2021.15系です。プロファイル時だけ`intel-vtune/2025.3.0`も読み込みます。

補助ツールのビルド用にGCC 16.1.0とccacheの`a89f5010f1c8edf231184b3a3a77654e12e4a288`を`~/.local`へ導入しています。玄界と同様に、`~/.local/.setenv`へ`PATH`、`LD_LIBRARY_PATH`、`MANPATH`、`PKG_CONFIG_PATH`などをまとめ、`~/.bashrc`から読み込みます。コンパイラを指定する環境変数はここで設定せず、OpenFOAMのコンパイラはIntel oneAPIのままとします。GCCの48並列ビルドはログインノードのメモリ不足で停止したため、GCCだけ16並列、ccacheは48並列とします。ソースと中間生成物は`/tmp`で作成して導入後に削除します。

GitHub Actions実行機の`/`は約124 MiBの読み取り専用zramで、作業領域の空き容量とは無関係です。Actionsの「Free space left: 88 MB」はこの`/`を見た警告です。実際の`_work`とOpenFOAMのデータは`/scratch/hb15`上にあります。2026年8月16日の`lquota`では、課題`hb15`の使用量は26.93 GiB / 1.00 TiB、inodeは75,868 / 202,000であり、いずれもクォータ内でした。この警告をクォータ超過と解釈しません。
