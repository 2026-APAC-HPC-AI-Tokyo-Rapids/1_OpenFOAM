# Gadiの運用設計

NCIのスーパーコンピュータ「Gadi」では、大量の小さなファイルを扱う処理と、長期間保持する大容量ファイルとを明確に分離して運用します。

- GitHub Actionsランナー本体は自宅サーバー（home-lab）上に配置し、`gadi-shell`を経由してGadiのログインノードへ処理を委譲します。Gadiログインノード側の`/tmp`は、ソースコードの展開、ビルド作業領域、およびccacheの一時作業領域として利用します。
- Gadiログインノードの`/dev/shm/ccache-${USER}`には、上限10 GBの一次ccacheを配置します。
- 共有ストレージの`/scratch/hb15/tk7779/openfoam/gadi`には、圧縮ソース、検証済み公式メッシュ、ビルド成果物、共有ccache、領域分割済みケースのアーカイブ、実行記録、および回収対象ファイルのみを配置します。
- PBS計算ノード上では、OpenFOAM実行環境および完全な領域分割済みケースを各ノードの高速ローカルストレージ`$PBS_JOBFS`へ展開します。展開後の実行環境、非分割メッシュ、`processor*`ディレクトリ群を`/scratch`上に直接配置することはしません。
- 玄界のビルド成果物やキャッシュをGadiで再利用することはありません。

Gadiの`/tmp`および`/dev/shm`は、ログインノード上の約126 GiBのtmpfsです。`/dev/shm`は`noexec`マウントされているため、実行バイナリの生成を伴うコンパイルや計算ジョブには使用できませんが、ccacheのキャッシュ保存先としては有効に機能します。ビルド終了時には`/tmp`上の展開物、中間生成物、ccacheの一時ファイルをクリーンアップし、`/dev/shm`の一次ccacheはログインノードが再起動等で破棄するまでの間、再利用します。

2026年8月23日に実施した4ノードでのプロファイル実行において、416ランクが共有`/scratch`上のeditable Pythonパッケージを一斉にインポートした際、`BrokenPipeError: [Errno 108] Cannot send after transport endpoint shutdown`が発生し、全ランクのラッパープロセスの起動が失敗しました（GitHub Actions実行 `32582110427`、PBSジョブ `177070111.gadi-pbs`）。この知見に基づき、計算ランクが実行する`experiment-metrics`およびプロファイル用ラッパーは、non-editable形式でインストールした後に単一アーカイブ化し、OpenFOAM実行環境と同時に各計算ノードの`$PBS_JOBFS`へ展開する方式へと変更しました。なお、ログインノード上で1度だけ実行される計測確定コマンドは、引き続きプロビジョニング領域を参照します。

OpenFOAM実行環境を1つ展開すると、約35,000〜37,000個のinodeを消費します。2026年8月17日に3件のワークフローを同時にプロビジョニングした際、プロジェクト`hb15`のinode上限値（212,100）に一斉に到達し、3件すべてが`tar: Disk quota exceeded`で異常終了しました（GitHub Actions実行 `32002206618`、`32002206644`、`32002207026`）。失敗した3件の展開ファイルを削除したところ、inode使用量は210,900から121,823へと回復しました。ビルド成果物のSHA-256ごとに実行環境を共有展開する暫定対処を行いましたが、領域分割済みケースを実行ごとに共有領域へコピーする運用でも同様にinode枯渇が発生しました。このため、共有領域への展開キャッシュおよび実行ごとのケース複製は全面的に廃止しました。

現行設計では、ケース準備ジョブ（PBS）のみが`$PBS_JOBFS`上で実行環境、公式メッシュ、全`processor*`ディレクトリを展開し、領域分割を完了したケース全体を単一の`case.tar.zst`としてアーカイブ化します。このアーカイブは、容量とSHA-256ハッシュを記録したメタデータとともに`case-archives`へ保存されます。通常計算のPBSジョブは、`$PBS_NODEFILE`から割り当てられたホスト群を特定し、各計算ノードの`$PBS_JOBFS`へ同一の実行環境アーカイブおよびケースアーカイブを展開します。各ランクは、自ノードの`$PBS_JOBFS`に存在する自身の`processor*`ディレクトリのみを読み書きします。複数ノード実行時のみ、OpenFOAMの補助ツールおよびソルバーに対して`-hostRoots`オプションを渡し、各ノードの先頭ランクを`-ioRanks`に指定します。動的コンパイルライブラリなど、ルート間で同期が必要なファイルへの書き込みは各ノードの1ランクのみが担当します。なお、1ノード実行時はすべてのランクが同一のジョブローカルファイルシステムを参照するため、分散ルート設定（`-hostRoots`）は有効化しません。アーカイブの検証と展開処理はソルバーの計測区間開始前に完了させ、公式のベンチマーク計測値には含めません。

各ノードへの`jobfs`要求量は100 GBです。PBSにおける`jobfs`指定はジョブ全体に対する要求量として扱われ、複数ノードへ均等に按分されるため、ジョブ投入スクリプトには`nodes * 100 GB`を指定します。ランクごとの実行管理情報の参照や配置情報の生成も各ノードの`$PBS_JOBFS`上で完結させ、ソルバー終了後に各ノードの代表1プロセスが配置情報および自ノード担当の`processor*`ディレクトリを共有領域へ回収します。回収された一時tarアーカイブ群は、ストリーム連結後に1度だけ圧縮され、`occDrivAerStaticMesh.foam`および全ランクの最終状態を含む単一の`paraview-case.tar.zst`として`RUN_DIR/large-output/paraview`配下に保存されます。`/scratch`上の実行ディレクトリに残すファイルは、ソルバーログ、公式判定結果、メトリクス断片、ハードウェアおよび配置記録、プロファイル出力などの回収対象データのみに限定しています。

32 KiBのファイルを4,096個作成する実測ベンチマークを実施した結果、所要時間は`/dev/shm`および`/tmp`が約0.08秒であったのに対し、`/scratch`は約5秒を要しました。この特性を踏まえ、一次ccacheを`/dev/shm`に配置し、別ログインノード間でも共有可能な共有ccacheを`/scratch/hb15/tk7779/openfoam/gadi/ccache`に配置しています。`~/.config/ccache/ccache.conf`において一次ccacheの上限を`max_size = 10GB`に設定し、共有ccacheについてはビルド完了後に`ccache --trim-dir`を実行して10 GB以内に整理します。`max_size`設定は共有ccacheには直接適用されず、また容量ベースの整理ではinode数が制限されないため、初回ビルド完了後に共有ccacheのファイル数も確認しています。

OpenFOAMのビルドは、ログインノード上のランナーにおいて16並列で実行します。物理24コアのCPUソケット2基（計48コア）に合わせて48並列で実行した場合、公式v2512のライブラリ群をIntel `icpx`でコンパイルする際に複数のコンパイラプロセスがメモリ不足（OOM）等により強制終了された実績があります（GitHub Actions実行 `31990408500`、2026年8月17日）。論理コア数ではなく実測に基づくメモリ制約を考慮し、GCC導入時にも安定して完走した16並列を採用しています。なお、環境変数`OMP_NUM_THREADS=1`の影響で`nproc`コマンドが1を返す環境であるため、並列数の自動決定には`nproc`を使用しません。

Gadiの計算ノードから外部ネットワークへは直接接続できません。そのため、実行中に採取したメトリクス断片は`/scratch`上の実行ディレクトリ内に一時記録し、PBSジョブ終了後にログインノード上のランナーから一括してBigQueryへ送信します。計算ノード環境に対してBigQueryの認証情報を環境変数等で渡すことはしません。

自宅サーバー（home-lab）のランナーはコンテナ単位で動作しており、SSH設定およびカスタムシェル（`gadi-shell`）を読み取り専用で参照します。Gadi側にGitHub Actionsランナー本体を常駐させることはしません。接続経路の正本ドキュメントは、home-lab環境の`/home/tomokazu/actions-runner/README.md`にあります。

PBSの投入先キューは、課題`hb15`配下の`normalsr`です。ジョブの投入、待機、終了判定、リソース指定はGadi専用のスクリプトとして完全に分離し、玄界のPJM用スクリプトと混同しない構造にしています。

ビルドおよび計算実行には`intel-compiler-llvm/2025.1.1`および`intel-mpi/2021.15.0`を使用します。これは玄界環境と同じIntel C++ 2025.1.1およびIntel MPI 2021.15系です。プロファイル計測時のみ、追加で`intel-vtune/2025.3.0`をロードします。

Gadiの計算ノードではIntel VTuneのサンプリングドライバが有効化されていません。2026年8月23日に実施した`hpc-performance`および`memory-access`のプロファイル実行では、ソルバー自体は公式のVALID判定まで完走したものの、VTune側でメモリ帯域の収集を開始できず終了コード1で失敗しました。このため、GadiにおけるHPC Performance Characterizationでは`collect-memory-bandwidth=false`を設定してドライバレス（driverless）のコアイベントのみを収集し、ノード全体のアンコア帯域（uncore bandwidth）は報告対象外としています。標準のMemory Access解析によるノード全体帯域の計測はGadi環境では実施不能として扱い、選択ランクに対するメモリアクセス特性の解析には、正常に採取可能な`memory-access-core`（Perf driverless/PEBS方式）を採用します。なお、玄界ではサンプリングドライバによる帯域収集実績があるため、従来通り帯域収集を有効（true）としています。

補助ツールのビルド用として、GCC 16.1.0およびccache（コミット `a89f5010f1c8edf231184b3a3a77654e12e4a288`）を`~/.local`配下に導入しています。玄界と同様に、`~/.local/.setenv`において`PATH`、`LD_LIBRARY_PATH`、`MANPATH`、`PKG_CONFIG_PATH`などを設定し、`~/.bashrc`からこれを読み込みます。このスクリプト内ではコンパイラを指定する環境変数は設定せず、OpenFOAMのビルドには常にIntel oneAPIコンパイラが使用されるようにしています。GCC自体の48並列ビルドはログインノードのメモリ不足で停止した実績があるため、GCCは16並列、ccacheは48並列でビルドを実施しています。ソースコードと中間生成物は`/tmp`上で処理し、インストール完了後にすべて削除します。

以前Gadiログインノード上に直接配置していたランナー環境では、約124 MiBの読み取り専用zramである`/`を検知して「Free space left: 88 MB」という警告が出力されていました。当時のワークスペース（`_work`）およびOpenFOAMの実データは`/scratch/hb15`上に配置されており、2026年8月16日時点の`lquota`は容量26.93 GiB / 1.00 TiB、inode 75,868 / 202,000でした。この過去の警告メッセージは、現在のhome-labランナーの容量やGadiの最新クォータ状況を示すものではありません。
