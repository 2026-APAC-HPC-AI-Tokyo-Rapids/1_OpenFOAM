# Gadiの運用

Gadiでは、小さなファイルを大量に配置する処理と、長期間保存する大容量ファイルを明確に分離します。

- ログインノード上のGitHub Actionsランナーの`/tmp`には、ソースの展開先、ビルド作業領域、ccacheの一時ファイルを置きます。
- ログインノード上のランナーの`/dev/shm/ccache-${USER}`には、10 GBを上限とする一次ccacheを置きます。
- `/scratch/hb15/tk7779/openfoam/gadi`には、圧縮ソース、検証済み公式メッシュ、ビルド成果物、共有ccache、領域分割済みケースのアーカイブ、実行記録と回収対象ファイルのみを置きます。
- PBS計算ノードでは、OpenFOAM実行環境と完全な領域分割済みケースを各ノードの`$PBS_JOBFS`へ展開します。展開後の実行環境、非分割メッシュ、`processor*`ディレクトリは`/scratch`へ置きません。
- 玄界の成果物やキャッシュをGadiで再利用しません。

Gadiの`/tmp`と`/dev/shm`はログインノード上の約126 GiBのtmpfsです。`/dev/shm`は`noexec`のため実行ファイルを生成するビルドや計算には使いませんが、ccacheの保存には使用できます。ビルド終了時に`/tmp`の展開物、中間生成物、ccacheの一時ファイルを削除し、`/dev/shm`の一次ccacheはログインノードが保持する間だけ再利用します。

OpenFOAM実行環境1件の展開には約35,000〜37,000 inodeを消費します。2026年8月17日に3件のワークフロー実行を同時にプロビジョニングしたところ、`hb15`のinode上限212,100に一斉に到達し、3件とも`tar: Disk quota exceeded`で失敗しました（Actions実行 `32002206618`、`32002206644`、`32002207026`）。失敗した3件の展開物を削除するとinode使用量は210,900から121,823へ戻りました。ビルド成果物のSHA-256ごとに実行環境を共有展開する暫定策でも、領域分割済みケースを実行ごとに共有領域へコピーすると同様にinode制約に衝突しました。このため、共有展開キャッシュと実行ごとのケース複製は廃止します。

ケース準備のPBSジョブだけが`$PBS_JOBFS`へ実行環境、公式メッシュ、全`processor*`ディレクトリを展開し、完全な領域分割済みケースを単一の`case.tar.zst`として、容量とSHA-256を記録したメタデータとともに`case-archives`へ保存します。通常実行のPBSジョブは`$PBS_NODEFILE`から割当ホストを特定し、各ノードへ同じ実行環境アーカイブとケースアーカイブを展開します。各ランクは同じノードの`$PBS_JOBFS`にある自身の`processor*`ディレクトリを読み書きします。複数ノード実行時のみOpenFOAMの補助処理とソルバーへ`-hostRoots`を渡し、各ノードの先頭ランクを`-ioRanks`に指定します。動的コンパイルライブラリなどルート間で配布するファイルは、1ノードにつき1ランクのみが書き込みます。1ノード実行では全ランクが同一のジョブローカルファイルシステムを参照するため、分散ルートを有効化しません。アーカイブの検証と展開はソルバー計測区間の前に完了させ、通常計測値には含めません。

`jobfs`要求は各ノード100 GBです。PBSの`jobfs`はジョブ全体への要求値であり複数ノードへ按分されるため、ジョブ投入時には`nodes * 100 GB`を指定します。ランクごとの実行管理情報の参照と配置情報の生成も各ノードの`$PBS_JOBFS`上で行い、ソルバー終了後に各ノードの1プロセスだけが配置情報と自ノード担当の`processor*`を共有領域へ回収します。後者の一時tarはストリーム連結後に一度だけ圧縮し、`occDrivAerStaticMesh.foam`と全rankの最終状態を含む単一の`paraview-case.tar.zst`にして一時プロファイル領域へ残します。`/scratch`上の実行ディレクトリに残すのは、ソルバーログ、公式判定結果、計測値の断片、ハードウェアと配置の記録、プロファイル出力などの回収対象のみです。

32 KiBのファイルを4096個作成した実測ベンチマークでは、`/dev/shm`と`/tmp`が約0.08秒、`/scratch`が約5秒でした。一次ccacheを`/dev/shm`、別ログインノードからも利用する共有ccacheを`/scratch/hb15/tk7779/openfoam/gadi/ccache`に配置します。`~/.config/ccache/ccache.conf`で一次ccacheを`max_size = 10GB`とし、共有ccacheはビルド後に`ccache --trim-dir`で10 GBまで整理します。`max_size`は共有ccacheには適用されず、容量による整理ではinode数も保証されないため、初回の実ビルド後に共有ccacheの実際のファイル数も確認します。

ビルドはログインノード上のランナーで16並列にて実行します。24物理コアのソケット2基に合わせた48並列では、公式v2512のライブラリ群をIntel `icpx`でビルドした際に複数のコンパイラプロセスが同時にOOM等で強制終了されました（Actions実行 `31990408500`、2026年8月17日）。CPUコア数ではなく実測したメモリ制約に基づき、GCC導入時にも完走実績のある16並列を採用します。環境変数`OMP_NUM_THREADS=1`の影響で`nproc`が1を返すため、並列数の自動決定には使いません。

計算ノードから外部ネットワークへの直接接続はできません。実行中の計測値断片は`/scratch`上の実行ディレクトリへ記録し、PBSジョブ終了後にログインノード上のランナーから一度だけ送信します。計算ノードへBigQueryの資格情報を環境変数等で渡すことはしません。

GitHub Actionsランナーは、バージョンごとに用意した`shared/<version>/externals`を共有します。共有物の初回作成とバージョンの切り替えは運用者が手作業で行い、ワークフローや起動スクリプトから自動で作成・更新しません。各ランナーの`bin`、認証情報、診断ログ、作業領域は共有しません。

PBSの投入先は課題`hb15`の`normalsr`です。投入、待機、終了確認、資源指定はGadi専用スクリプトに分離し、PJM用の処理と混同しません。

ビルドと実行には`intel-compiler-llvm/2025.1.1`と`intel-mpi/2021.15.0`を使用します。これは玄界と同じIntel C++ 2025.1.1、Intel MPI 2021.15系です。プロファイル取得時のみ`intel-vtune/2025.3.0`も読み込みます。

補助ツールのビルド用にGCC 16.1.0とccacheの`a89f5010f1c8edf231184b3a3a77654e12e4a288`を`~/.local`へ導入しています。玄界と同様に、`~/.local/.setenv`へ`PATH`、`LD_LIBRARY_PATH`、`MANPATH`、`PKG_CONFIG_PATH`などをまとめ、`~/.bashrc`から読み込みます。コンパイラを指定する環境変数はここでは設定せず、OpenFOAMのコンパイラはIntel oneAPIのままとします。GCCの48並列ビルドはログインノードのメモリ不足で停止したため、GCCのみ16並列、ccacheは48並列でビルドします。ソースと中間生成物は`/tmp`上で作成し、導入完了後に削除します。

GitHub Actionsランナーの`/`は約124 MiBの読み取り専用zramであり、作業領域の実際の空き容量とは無関係です。Actionsの「Free space left: 88 MB」はこの`/`を検知した警告です。実際の`_work`およびOpenFOAMのデータは`/scratch/hb15`上に配置されています。2026年8月16日の`lquota`確認では、課題`hb15`の使用量は26.93 GiB / 1.00 TiB、inodeは75,868 / 202,000であり、いずれもクォータ内でした。この警告をクォータ超過と誤認しないようにします。
