# ccache一次キャッシュの共有領域への再共有（同期）

## 結論

新規ビルドを実行することなく、ログインノード上の一次キャッシュからファイルバックエンド（file backend）の共有キャッシュへ未登録エントリを安全に同期できる。同期スクリプト `scripts/reshare-file-ccache.py` は、一次キャッシュ内を走査し、自己完結（self-contained）しているエントリのみを抽出して共有キャッシュのディレクトリ配置へアトミックに追加する。既存エントリの上書きは行わず、また一次キャッシュ側のエントリを削除することもない。

本同期プログラムは、通常のビルドパイプラインには組み込まない。2026年8月16日以降、玄界・Gadi両クラスタの `~/.config/ccache/ccache.conf` において `reshare = true` を常時有効化しており、ローカルキャッシュヒット時にもccache自身が共有先へ自動的に書き戻しを行う。ワークフロー入力や環境変数による動的切り替えは設けない。同期スクリプトは、共有ストレージの一時的な障害復旧時や、共有設定が有効化される前に作成された古い一次キャッシュを回収する場合に限り、手動で実行する。

## 技術的背景と設計根拠

両クラスタで使用しているccacheは、公式リポジトリのコミット `a89f5010f1c8edf231184b3a3a77654e12e4a288` である。このバージョンにおける `reshare = true` は、コンパイル要求が一次キャッシュにヒットした際、そのエントリを共有ストレージ側へ書き戻す設定項目であり、全エントリを一括同期するCLIコマンドを提供するものではない。

ファイルバックエンドに保存されるエントリデータは一次キャッシュと同一のバイト列であるが、ディレクトリの配置ルールが異なる。40桁のキャッシュキーを `012345...` とした場合、現在の一次キャッシュは `0/1/2345...` に配置されるのに対し、ファイルバックエンド側は `01/2345...` に配置される。したがって、ディレクトリ全体の単純なコピー（`cp -r` 等）は利用できない。また、一次キャッシュ内に存在する `stats`、`CACHEDIR.TAG`、および一時作業ファイルを共有先へ混入させてはならない。

ccacheは、共有先への書き戻しを行う前にエントリヘッダーの `self_contained` フラグを検証する。本同期プログラムも同一の判定条件を採用している。ファイルバックエンドを有効化したビルドではraw file方式が無効化されるため、実機で確認したGadiの3,574エントリおよび玄界の24,384エントリはすべて自己完結していた。また、両クラスタとも正常ビルドによって生成されたエントリは、全件がすでに共有側に存在していることを確認した。

## 実行手順

一次キャッシュはノードローカルな `/dev/shm` 上に存在するため、当該キャッシュを保持しているログインノード上で個別に実行する。

Gadi環境での実行例：

```bash
uv run --script scripts/reshare-file-ccache.py "/dev/shm/ccache-${USER}" "/scratch/hb15/${USER}/openfoam/gadi/ccache"
ccache --trim-dir "/scratch/hb15/${USER}/openfoam/gadi/ccache" --trim-max-size 10GB
```

玄界環境での実行例：

```bash
uv run --script scripts/reshare-file-ccache.py "/dev/shm/ccache-${USER}" /fast/pj26000080/ccache_cache_dir
```

ファイルの複製を行わず対象件数のみを走査する場合は `--dry-run` オプションを付与する。なお、本プログラムは共有キャッシュの容量整理（trim）は行わない。Gadiにおける10 GB上限のようなストレージポリシーの適用は、同期完了後にccache自身の `--trim-dir` コマンドを用いて行う。

## ウォームビルドにおける性能影響

2026年8月16日にGitHub Actions実行 [`31948680575`](https://github.com/2026-APAC-HPC-AI-Tokyo-Rapids/1_OpenFOAM/actions/runs/31948680575) において性能比較を実施した。各クラスタにおいて同一ログインノード上のランナーを占有し、初回の `reshare = false` をウォームアップとして除外した上で、`false, true, true, false, false, true` の順序で交互に測定した。各試行はクリーンなビルドツリーを使用し、一次ccacheのみを同一の `/dev/shm/ccache-${USER}` から再利用した。

測定した全試行において、1,789 cacheable calls、1,785 local hits、4 misses で統計が完全一致した。`remote_storage_write` は `false` 時に8件、`true` 時に3,574件であり、`true` 設定下でローカルヒットエントリの共有先への書き戻しが実際に発生していることを確認した。

| クラスタ | `reshare` 設定 | ビルド本体所要時間（3試行、秒） | 中央値（秒） | ビルドジョブ全体中央値（秒） |
|---|---|---:|---:|---:|
| Gadi | `false` | 249.630, 245.759, 251.784 | 249.630 | 259.578 |
| Gadi | `true` | 244.304, 267.312, 248.953 | 248.953 | 259.633 |
| 玄界 | `false` | 299.140, 304.140, 300.497 | 300.497 | 350.584 |
| 玄界 | `true` | 319.579, 311.158, 298.461 | 311.158 | 364.854 |

Gadi環境では、ビルド本体の中央値が0.677秒短縮、ジョブ全体では0.055秒増加した。いずれも差分は0.3%未満であり、`true` 試行内における自然な変動幅よりも小さいため、有意な性能劣化は検出されなかった。

玄界環境では、`true` 設定によりビルド本体の中央値が10.661秒（3.55%）増加し、ジョブ全体の中央値が14.270秒（4.07%）増加した。ただし `true` 側の所要時間範囲（298.461秒〜319.579秒）は `false` 側の範囲と重複しており、3回の試行のみから確定的な遅延率を結論付けることはできない。実際の運用においては、この測定結果を記録に残した上で、複数ランナー環境において共有キャッシュを常に最新状態に補完できる運用の利便性を最優先とし、両クラスタの設定ファイルにおいて `reshare = true` を維持する方針とする。
