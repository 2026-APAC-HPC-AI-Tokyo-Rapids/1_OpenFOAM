# 試行から得られた判断と知見

この記録は、2026-05 から 2026-07 にワークフローと GitHub Actions 実行で確認した事項を、現在の意思決定に活用できる形に整理したものである。性能値の多くは OpenFOAM v2412 での試行結果であり、現在の v2512 / v2606 と直接比較できる値ではない。また数値は共有ランナー上の観測値であり、他環境での性能を保証するものではない。

## 1. 再現可能なフルビルドの確立

初期段階ではソースコードの配置、OpenFOAMの環境初期化、ADIOS2 / CGALのバージョン選定、FFTWのリンクパス、ccacheの適用、ログ収集方法を順次改善した。フルビルドを成立させるには、単にコンパイラを指定するだけでなく、OpenFOAMが要求するThirdPartyの配置とリンク時のライブラリ探索パスを整合させる必要があった。

現在確定している方針は以下のとおりである。

- ソースアーカイブは共有キャッシュから展開し、展開済みソースと中間生成物は実行ごとにクリーンに作成する。
- OpenFOAMの `bashrc` 読み込み時のみシェルの `-e` / `-u` を一時的に解除する。OpenFOAM自身の初期化スクリプトが未定義変数や中間的な非ゼロ終了を許容する設計になっているためである。
- `Allwmake -log` の終了ステータスを確実に捕捉できるよう `bash -o pipefail` で実行する。失敗したビルドを誤って成功扱いしないことを、コンソール出力の簡潔さよりも優先する。
- 詳細なビルドログはアーティファクトとして保存する。大量の通常出力をコンソールに流さず、失敗時のみエラー要約を出力する。

## 2. ビルド並列度は 120 を基準とする

30、60、90、120 の `Allwmake -j` を比較した。観測された中央値はそれぞれ 19分46秒、18分21秒、20分17秒、16分26秒であった。少なくともこの比較条件においては 120 が最良であり、60 や 90 へ下げても安定化の向上は見られなかった。

したがって現在は `-j 120` を標準としている。ただしこれは「120 があらゆる環境で常に最速」という一般則ではない。共有ランナー上では I/O やメタデータアクセスの競合が大きく、試行回数が少ない設定間の微小差には環境の揺らぎが含まれる。160 以上は未検証であり、変更する場合は複数回の交互実行によって評価する。

## 3. キュー制御なし、GNU リンカーを維持する

`Allwmake` のキュー制御の有無および lld リンカーを検証した。

- ccache がウォームな状態では、キュー制御を導入してもビルド全体の短縮効果は確認できなかった。現在はキュー制御なしとしている。
- Icx から lld を使用するために OpenFOAM のリンク規則にパッチを適用し、`--allow-shlib-undefined` 等を含めて互換性を検証した。部分的に成功する実行はあったものの、フルビルドにおいてリンク失敗が再発した。
- GNU ld はフルビルドの安定成功を継続している。lld を維持するに足る安定した短縮効果が得られなかったため、lld 用パッチは撤去した。

この判断はリンカー単体の優劣ではなく、対象とする OpenFOAM バージョン、Icx、Intel MPI、ThirdParty の組み合わせにおける保守性と安定性を重視した結果である。

## 4. ccache は有効だが、ビルド時間全体を支配しない

ccache のウォームビルドにおけるヒット率は約 99.5% に達する。実際の再コンパイルを大幅に削減できるため、ccache は不可欠である。

一方で、キャッシュ全体を実行ごとに tmpfs へコピーする方式はコピー処理自体に約82秒を要し、ビルド所要時間の中央値は 24分26秒となった。ランナー既定のストレージ領域を使用する方式は 16分26秒、事前に tmpfs に配置したキャッシュは 16分09秒であった。後者の差は実行間の環境変動幅より小さく、永続キャッシュを毎回メモリへコピーする複雑さを正当化しない。

ccache がヒットした場合でも、依存関係の解決、ディレクトリ走査、リンク、インストール、多数の短命プロセスの起動オーバーヘッドは残る。したがってヒット率の高さのみをもって「ビルド時間が極小になるはず」と判断してはならない。

## 5. 所要時間の変動は外部環境要因として扱う

同一の 120 並列、同一ソース、同等の ccache ヒット率であっても、`Allwmake` の所要時間は約14分台から23分台まで変動した。

比較例として、通常実行 `28992544864` ではジョブ全体が 15分47秒、`Build OpenFOAM` ステップが 14分43秒であった。一方、同一条件の実行 `29015734524` ではジョブ全体が 24分17秒、ビルドステップが 23分09秒であった。チェックアウト、展開、アーカイブ作成、アップロードの所要時間に差はなく、増加した約8分半のほぼすべてがビルドステップで発生している。ccache ヒット率はいずれも 99.50% であった。

この結果から、共有ファイルシステム、コンパイラ/ヘッダーの参照、ccache ストレージなど、tmpfs 外部の共有計算資源の競合による遅延が発生していると考えられる。

結論として、単一実行の実時間（wall time）のみを改善効果の根拠としてはならない。最適化候補は同一条件で複数回測定し、各ステップの所要時間、ログの工程タイムスタンプ、ccache の統計情報を総合して判断する。

## 6. バージョン更新とビルドパスの正規化

OpenFOAM のバージョン更新時、バージョン名付きのソースディレクトリをそのまま使用すると、`CCACHE_BASEDIR` から見た相対パスにバージョン名が含まれ、キャッシュキーが分離してしまう。そこで展開後のディレクトリ名を `OpenFOAM` および `ThirdParty` に正規化した。

統計情報の誤認を防ぐため、`Allwmake` の実行直前に `ccache --zero-stats` を実行して統計を初期化する。

## 7. ビルド成果物の再利用管理

※本節は成果物再利用の仕組みを確立した当時の記録である。現在は新規ビルドのみをプッシュ時のコミットメッセージ `[require-build]` で指定し、それ以外は自動的に第一親コミットを遡って利用可能な成果物を再利用する。手動実行時はコミットメッセージを読まない。

ワークフローは第一親コミットを1コミットずつ遡り、正常に作成されたビルドアーカイブを探索する。差分から互換性を推測する複雑な判定は行わず、コミット履歴に基づく明確な再利用ルールとしている。
