# 現在のビルド構成

本稿では九州大学「玄界」におけるOpenFOAMのビルド構成を解説する。NCI「Gadi」はコンパイラ、MPI、ストレージ構成が異なるため、[Gadi用ワークフロー](../../.github/workflows/gadi.yml)および[運用設計](../../platforms/gadi/README.md)を参照のこと。

## ビルドの諸元

| 項目 | 設定値・内容 |
|---|---|
| OpenFOAM | OpenFOAM.com v2512（`OpenFOAM-v2512`タグ） |
| 追加依存関係 | Scotch 6.1.0 |
| コンパイラ / MPI | `intel/2025.1.3`モジュール（Intel C++ 2025.1.1、Intel MPI 2021.15） |
| Makeプリプロセッサ | 計算ノードでも動作可能なgcc-toolset-11環境の`/opt/rh/gcc-toolset-11/root/usr/bin/cpp` |
| OpenFOAM設定 | `WM_COMPILER=Icx`、`WM_MPLIB=INTELMPI`、倍精度（DP）、32ビットラベル（label32） |
| ビルド対象 | `simpleFoam`、公式の前処理・検証用ツール群、計測用補助ツール |
| コンパイラキャッシュ | ccache（CMakeによるC/C++コンパイル呼び出しにも適用） |

組織管理下のソースリポジトリは読み取り専用として扱い、OpenFOAMは`OpenFOAM-v2512`、ThirdPartyは`v2512`のタグから特定のブランチに依存しないdetached状態で取得する。公式ソースコードへの直接の計測処理埋め込みは行わず、通常計測では改変のない標準ソルバーを使用する。プロファイル計測時は、実行時に指定したランクに対してのみIntel VTuneをアタッチする。

## ディレクトリとキャッシュの配置設計

ビルドに関わるストレージ領域は、以下の3系統に明確に分離している。

| 種別 | 配置場所 | 運用の意図 |
|---|---|---|
| ソースアーカイブ | 共有ソースキャッシュ領域 | ダウンロード済みアーカイブを再利用し外部ネットワーク負荷を低減する |
| 展開済みソース・オブジェクト・ログ | 各実行固有の`/dev/shm/openfoam-<run-id>-...` | ビルドツリーで発生する大量のI/Oをランナーのメモリ上（tmpfs）に閉じ込める |
| ccache永続データ | ランナー既定の共有キャッシュ領域 | ウォーム状態のコンパイルキャッシュを実行間で安全に再利用する |
| ccache一時ファイル | 実行用一時ディレクトリ内の`ccache` | 一時ファイルを永続成果物から確実に分離する |
| ビルド成果物アーカイブ | 共有ビルド成果物ディレクトリ | 実行番号（Run ID）ごとの`tar.zst`を後続ジョブから利用可能にする |

アーカイブ展開後のバージョン番号付きディレクトリ名は、ビルドルート直下の`OpenFOAM`および`ThirdParty`へと正規化する。`OpenFOAM/ThirdParty`は後者へのシンボリックリンクとして構成し、OpenFOAMの標準的な探索ルールを維持する。さらに`CCACHE_BASEDIR`をビルドルートに指定することで、実行ごとの一時パスやOpenFOAMのバージョン文字列がキャッシュキーに混入することを防止する。ジョブ終了時のクリーンアップは、当該実行IDに紐づく`mktemp`ディレクトリのみに限定する。

なお、`/dev/shm`の利用はビルドツリー自体のI/Oを高速化する手段であり、すべてのI/Oを完全に分離するものではない。コンパイラバイナリ、システム標準ヘッダー、環境モジュール、およびccacheの保存領域は依然として共有ストレージ側に存在する。そのため、ビルドルートをtmpfsに配置した場合であっても、ストレージの負荷変動による所要時間の揺らぎは依然として発生する。

## ビルド成果物の生成と再利用制御

ビルド成果物は`${BUILD_ARCHIVE_DIR}/${GITHUB_RUN_ID}.tar.zst`として保存される。プッシュ実行時のみ、最新コミットメッセージの先頭に`[require-build]`タグを付与することで強制的な新規ビルドを指示できる。手動実行（workflow_dispatch）時はコミットメッセージのタグを参照しない。

成果物を再利用する際は、現在のコミットから第一親（first-parent）を1コミットずつ過去へ遡る。GitHub Actions全体の実行履歴を実行日時順に走査するのではなく、各コミットに紐づく`OpenFOAM`ワークフローの実行履歴を新しい順に検証する。再利用の可否は`scripts/build-inputs-match.sh`により判定し、サイドカーファイルに記録された元のビルドコミットと現在のコミットを比較して、OpenFOAM/ThirdPartyのソース、共通およびクラスタ別のビルド設定、ネイティブツール群、ビルド対象プローブのいずれにも差分がないことを確認する。アーカイブファイルとサイドカーメタデータが同一クラスタ上に存在し、記録された容量およびSHA-256ハッシュが一致する最初の成果物が見つかった場合、それを現在の実行番号へハードリンクして再利用する。利用可能な成果物が存在しない場合は新規ビルドを実行する。ビルド成果物に影響を与える変更を行った場合は、プッシュ時に`[require-build]`を付与して明示的に新規ビルドを要求する運用とする。

計算実行ジョブでは、選定された成果物アーカイブを展開し、ケース準備、計算ジョブの実行、公式結果判定、メトリクス収集、成果物回収までを同一のActions実行内で一貫して完了させる。

## 実行時の観測ポイント

正常終了したビルドでは、以下の観測項目を確認する。

- GitHub Actionsのジョブおよびステップ所要時間: ランナーのキュー待機時間と実際の`OpenFOAMをビルド`ステップの所要時間を区別して把握する。
- 成果物内の`allwmake.log`: `3_OpenFOAM_Src`内のAllwmakeロギング処理によって各行にタイムスタンプが付与されるため、ボトルネックとなった工程を特定できる。
- `ccache --show-stats`: `Allwmake`実行直前に統計をゼロ初期化しているため、当該ビルドにおけるキャッシュヒット率、キャッシュ対象呼び出し数、ミス数、ローカル/リモートの保存状況を正確に把握できる。
- 失敗時の`allwmake.log`およびActionsエラー出力: ワークフロー側でコンソール上にエラー要約を表示しつつ、完全なログファイルはアーティファクトとして確実に保存する。

ビルド処理本体は`scripts/build-openfoam-task.sh`を直接呼び出す構成とし、定常的なプロファイラ等は介在させない。詳細なプロファイル測定が必要な場合は、比較条件を固定した検証専用のコミットを作成して実施する。
