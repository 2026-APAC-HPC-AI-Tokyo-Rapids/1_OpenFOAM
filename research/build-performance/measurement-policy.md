# ビルド性能の測定および比較方針

## 実験前に固定・記録すべき条件

ビルド性能の比較評価を実施する際は、少なくとも以下の項目を固定または記録する。

- ワークフローを実行するコミットのSHAハッシュおよび適用パッチの内容
- OpenFOAM、ADIOS2、CGAL、Intel oneAPI、Intel MPIの各バージョン
- `WM_NCOMPPROCS`、ビルドスクリプトの引数、キュー設定、リンカー設定、ccache設定
- 実行の開始時刻、各ジョブおよびステップの所要時間、終了ステータス（成否）
- `ccache --show-stats`により出力されるキャッシュヒット率および呼び出し回数

測定対象とするパラメータは、一度の比較において原則1つに限定する。たとえばコンパイル並列度を変更する実験では、ccacheの配置場所やリンカーの種類を同時に変更してはならない。

## 基本的な実験手順

1. 基準構成（ベースライン）を少なくとも2回実行し、実行環境に起因するばらつきをあらかじめ把握する。
2. 変更構成を基準構成と同回数実行する。
3. 可能な限り、基準・変更・基準・変更の順序で交互に実行し、時間帯による共有システムの負荷の偏りを平滑化する。
4. GitHub Actionsの`Build OpenFOAM`ステップの所要時間と、アーティファクト内の`allwmake.log`に記録されたタイムスタンプを比較・分析する。
5. ccacheのヒット率やミス数に変動が見られる場合は、経過時間（wall-clock time）とは独立した要因として記録する。
6. ジョブの成否判定のみならず、生成された成果物アーカイブおよびログファイル群が意図通りに保存されていることを検証する。

比較結果をまとめる際は、中央値（median）に加えて最小値および最大値を併記する。単発の最小値（ベストスコア）のみを採用の根拠としてはならない。

## 今後の検討候補

検証の優先順位は、単なる「時間短縮の可能性」だけでなく、動作の正当性および長期的な保守コストを総合的に考慮して決定する。

| 検討候補 | 期待される効果 | 留意事項・リスク |
|---|---|---|
| ThirdParty成果物のアーカイブキャッシュ化（バージョン／コンパイラ／パッチハッシュ単位） | 初回フルビルドの固定時間を大幅に削減できる可能性がある | ABI互換性、RPATH設定、再配置可能性（relocatability）の厳密な検証が必要 |
| 160以上の高並列度 | I/O待ちを効果的に隠蔽できる可能性がある | 共有ランナー上ではCPUおよびストレージ負荷の集中によりかえって性能が悪化する恐れがあるため、複数回の交互比較が必須 |
| `CCACHE_SLOPPINESS=system_headers` の適用 | システムヘッダーの検証処理を省略しオーバーヘッドを削減できる可能性がある | キャッシュの正確性に与える影響を検証するため、専用のA/Bテストを実施して安全性を確認する |
| `CCACHE_NOSTATS=1` の設定 | 統計情報更新に伴うファイルI/Oを削減できる可能性がある | キャッシュの観測性が低下するため、通常運用に組み込む前に実効性を慎重に検証する |
| OpenFOAMビルドツリーの再利用 | 依存関係生成、オブジェクト生成、リンク処理を大幅に省略できる可能性がある | キャッシュ無効化（invalidation）の判定条件が極めて複雑であり、不整合の発生を防ぐ厳密な設計が要求される |

なお、ccacheのキャッシュ全体を実行ごとにtmpfsへコピーする案や、lldリンカーを常用する案については、現時点では再検討の優先度を下げる。前者はキャッシュのコピー処理自体に要するオーバーヘッドが大きく、後者はフルビルドにおける互換性と安定性がGNU ldに及ばないことが確認されているためである。

## 本調査の対象外事項

本調査では、以下の項目をビルド性能評価の対象外として明確に区別する。

- OpenFOAMソルバー自体の計算実行時間や並列スケーリング性能
- MPI通信性能、ノード間インターコネクト性能、GPUアクセラレーション
- 計算結果の物理的・数値流体力学的な妥当性
- 玄界全体の混雑状況の客観的な断定

GitHub Actionsの実行ログのみから共有クラスタ全体の混雑度を直接観測することはできない。ビルドの遅延が発生した場合は、まずワークフロー内の各処理工程およびccacheの動作状態を確認し、それでも説明がつかない遅延についてのみ「共有環境の混雑に伴う一時的な変動の可能性」として記録する。
