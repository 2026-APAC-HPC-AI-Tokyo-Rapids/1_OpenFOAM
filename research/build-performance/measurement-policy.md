# ビルド性能の測定・比較方針

## 変更前に固定するもの

性能比較では、少なくとも以下の項目を固定または記録する。

- ワークフローのコミットSHAとパッチ内容
- OpenFOAM、ADIOS2、CGAL、oneAPI、MPIの各バージョン
- `WM_NCOMPPROCS` とビルドスクリプト引数、キュー設定、リンカー、ccacheの設定
- 実行の開始時刻、ジョブ / ステップ所要時間、成否
- `ccache --show-stats` によるヒット率と呼び出し数

測定対象は一度に1つだけ変更する。例えば並列度を変える実行では、ccacheの配置やリンカーを同時に変更しない。

## 基本的な実験手順

1. 基準構成を少なくとも2回実行し、環境由来のばらつきを事前に確認する。
2. 変更構成を同じ回数だけ実行する。
3. 可能なら基準・変更・基準・変更の順に交互実行し、時間帯による負荷の偏りを減らす。
4. Actionsの `Build OpenFOAM` ステップ所要時間とアーティファクトの `allwmake.log` を比較する。
5. ccacheヒット率やミス数が変化していれば、実時間（wall time）と独立した要因として記録する。
6. 実行の成否だけでなく、生成されたアーカイブとログが期待どおり保存されていることを確認する。

結果は中央値および最小値・最大値を併記する。最小値（ベストスコア）のみを採用根拠としない。

## 検討対象の候補

優先順位は「短縮可能性」だけでなく、正当性と保守コストを考慮して決定する。

| 候補 | 期待される効果 | 注意点 |
|---|---|---|
| ThirdParty成果物をバージョン / コンパイラ / パッチハッシュでアーカイブキャッシュ化 | フルビルドの固定時間を大幅に削減できる可能性 | ABI、RPATH、再配置可能性（relocatability）の検証が必要 |
| 160以上の並列度 | I/O待ちを隠蔽できる可能性 | 共有ランナー上では負荷増により悪化する可能性もあるため複数回比較が必須 |
| `CCACHE_SLOPPINESS=system_headers` | ヘッダー検証処理を削減できる可能性 | キャッシュ正確性への影響を検証するため専用のA/Bテストを実施 |
| `CCACHE_NOSTATS=1` | 統計情報更新のI/Oを削減できる可能性 | 観測性が低下するため、通常運用に組み込む前に効果を検証 |
| OpenFOAMビルドツリーの再利用 | 依存関係生成 / オブジェクト生成 / リンクを省略できる可能性 | キャッシュ無効化（invalidation）条件が複雑で、誤った再利用を防ぐ厳密な設計が必要 |

ccache全体を実行ごとにtmpfsへコピーする案や、lldリンカーを常用する案は、現時点では再試行の優先度を下げる。前者はコピー自体のオーバーヘッドが大きく、後者はフルビルドでの互換性・安定性がGNU ldに劣るためである。

## 調査の範囲外

本調査では、以下をビルド性能の結論として扱わない。

- OpenFOAMソルバーの実行時間やスケーリング性能
- MPI通信性能、ノード間性能、GPU利用
- 計算結果の物理的・数値的な正当性
- 玄界全体の混雑状況の断定

Actionsログのみから共有システム全体の負荷を直接観測することはできない。ビルドが遅延した場合は、まずワークフロー内の工程とキャッシュ状態を確認し、それでも説明できない遅延を「共有環境の混雑による変動の可能性」として記録する。
