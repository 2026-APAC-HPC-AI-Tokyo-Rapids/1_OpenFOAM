# OpenFOAM motorBikeの実行性能調査

> [!NOTE]
> 過去の記録: 本調査はIssue #18における公式課題移行前に実施したものである。現在の公式課題は `benchmark/workload.json` に定義されたOpenFOAM.com v2512の `occDrivAerStaticMesh` であり、以下のmotorBikeケースの測定結果とは直接比較できない。

## 目的

本稿は、九州大学「玄界」においてOpenFOAM v2606の `simpleFoam` を用いたmotorBikeチュートリアルケースを実行し、実行時プロファイル計測および起動構成のチューニングを実施した結果を記録したものである。改善の対象はMPIプロセス配置、MPIおよびOpenFOAMのランタイム設定、ならびにプロファイラの起動オプションに限定し、OpenFOAMのソースコード自体は改変していない。

過去のApplication Performance Snapshot（APS）、Intel VTuneの完全な測定結果、および当時生成したParaView成果物は、GitHub Actionsのアーティファクトとは別に永続保管している。既存のParaView成果物は過去実行の履歴データとして保持するが、新規profile Actionsでは生成しない。旧 `openfoam-vtune` ディレクトリ配下も過去実行の履歴データとして保持している。

```text
~/openfoam-profile/<github-run-id>-<pjm-job-id>/
```

新規プロファイル実行における大容量成果物は以下のパスへ保存される。

```text
/hdd_raid/samba/net_share/openfoam-artifacts/<github-run-id>/<cluster>/openfoam-<cluster>-v2-<run-id>/large-output/vtune/vtune-result.tar.zst
```

共有プロファイル領域および各実行ディレクトリのパーミッションは `2770` に設定されている。本記録作成時点で、プロファイルデータ全体の容量は約3.0 GiBであった。

## 実験条件

- ソフトウェア環境: OpenFOAM v2606、`simpleFoam`、Intel oneAPI 2025.1.3、Intel MPI 2021.15。
- 基準ノード構成: 玄界CPUノード1台、MPI 120ランク。初期のスケーラビリティ調査およびプロファイル計測では最大2ノードを使用した。
- ハードウェア諸元: 1ノードあたり物理60コアのCPUソケット2基（計120物理コア、ハイパースレッディング有効時240論理CPU）。
- インターコネクト: APSの報告によるとConnectX-7（InfiniBand NDR200）。
- 領域分割方式: Scotch。
- 計算条件: `endTime = 3000`、計算終了時（`Time = 3000`）に結果フィールドを1回書き出す。
- メッシュ規模: 356,630セル、1,116,860面、408,877節点。
- 240 MPIランクに対してメッシュ規模が非常に小さい。
  - 240ランク: 1ランクあたり約1,486セル
  - 120ランク: 1ランクあたり約2,972セル
  - 60ランク: 1ランクあたり約5,944セル

メッシュはGitHub Actionsの実行ごとに再生成した。ソルバーの性能比較では同一ケースおよび計算時間を用いたが、共有HPCクラスタに不可避の実行間揺らぎを考慮して経過時間を評価する必要がある。

## 1ノード120ランク環境におけるMPIチューニング

標準的な運用条件は、1ノードあたり120 MPIランク（物理1コアあたり1ランク）の割り当てである。Intel MPI 2021.15は、同一ノード内の全ランク実行であっても通信を自動的に共有メモリ（shm）のみに限定しなかった。基準条件の診断ログを確認したところ、全ランクが単一ノード上にあるにもかかわらず、`mlx`（libfabric Mellanoxプロバイダ）が選択されていた。ジョブスクリプト `scripts/run-openfoam.pjm` において以下の環境変数を明示的に指定することで、不要なファブリックの初期化オーバーヘッドを排除できる。

```bash
export I_MPI_FABRICS=shm
```

各設定変更は個別のコミットとしてプッシュし、独立したActions実行およびPJMジョブとして計測した。表中の「起動全体」は、ソルバーの計算時間だけでなくMPIの初期化および終了処理を含めた全体の所要時間である。

| 実行 | MPI設定 | ソルバー時間 | 起動全体 | 評価結果・備考 |

| #142 | `I_MPI_FABRICS=shm` | **101 s** | **104.45 s** | 共有メモリ通信のみを指定した試行で最速を記録 |

| #145 | `I_MPI_ADJUST_ALLREDUCE=1`（再帰的倍加） | 未完了 | 未完了 | PJMの制限時間（25分）までにTime=943までしか進まずタイムアウト |

基準条件では、ランク0〜119が論理CPU 0〜119へ割り当てられていた。明示的に `core` ピニングを指定した場合も実効CPU一覧は同一となったため、配置順序による微小な時間差はピニングの優劣ではなく測定雑音と判断される。実際に有効であった改善要因は、ピニング方式ではなく通信ファブリックの選択（`I_MPI_FABRICS=shm`）であった。

実行 #152 では、共有メモリ設定をすべてのMPI前処理より前段階へ移動したことにより、Actionsのログ追跡区間の所要時間が基準条件（#141）の201秒から165秒へと大幅に短縮された。本設定を `simpleFoam` のみに適用していた初期試行では同区間に185〜189秒を要していた。この改善により、主ソルバーだけでなく `snappyHexMesh`、`topoSet`、`potentialFoam` の各前処理工程も高速化した。

なお、本ジョブにおいてAllreduceのアルゴリズムを一律に固定することは逆効果となった。OpenFOAMは計算状況やメッセージサイズに応じて多様なサイズでAllreduceを呼び出すため、Intel MPIが備えるメッセージ長別の自動選択アルゴリズムに任せるのが最も安定している。特に再帰的倍加（recursive doubling）は本環境に著しく不適合であり、ジョブ制限時間内に計算が完了しなかった。最終構成としては `I_MPI_FABRICS=shm` のみを明示指定し、プロセスピニング、集合通信アルゴリズム、および自動調整機能は既定値（デフォルト）のまま維持する方針とした。

本検証から得られた最大の知見は、プロセスピニングの微調整ではなく「ランク数の適正化」の重要性である。2ノード実行において総ランク数を240ランクから120ランク（各ノード60ランク）へと半減させた結果、ソルバー時間は105秒から56秒へと約47%短縮された。さらに60ランクまで減らすと並列度不足により76秒へ悪化した。165ランク程度まではソルバー単体の計算時間をわずかに短縮可能であるが、MPIプロセスの起動・終了オーバーヘッドがそれを上回る規模で増大する。120ランク構成は測定した起動全体の所要時間が最も短く、PJMジョブ全体の一連の処理時間においても最速であったため、運用上の標準構成として最適であると結論付けた。

ジョブ全体の所要時間に近いActionsのログ追跡時間は、240ランクで272秒、120ランクで133秒、60ランクで133秒、90ランクで138秒、135/150ランクで154秒、165ランクで171秒、180ランクで177秒であった。60ランクの総所要時間が120ランクと同等である理由は、ソルバー計算自体は遅いものの、プロセスの起動および前処理工程が軽量であるためである。120ランク構成は、ジョブ全体のオーバーヘッドを増大させることなくソルバーの並列計算処理量を最大化できるバランス点となっている。

## APSによる240ランク低速化のボトルネック分析

全ランクを対象としてApplication Performance Snapshot（APS）を適用した実行は #119（240ランク）および #133（120ランク）である。生データは以下のディレクトリに保存されている。

```text
~/openfoam-profile/30005026547-6264943/  # 240ランク
~/openfoam-profile/30007072403-6265018/  # 120ランク
```

| APS測定指標 | 240ランク構成 | 120ランク構成 |
| --- | ---: | ---: |
| 計測対象区間の経過時間 | 179.02 s | 86.62 s |
| 平均MPI経過時間 | 151.27 s（84.50%） | 51.80 s（59.86%） |
| MPI負荷不均衡（Imbalance） | 44.30 s（24.75%） | 15.57 s（18.00%） |
| `MPI_Allreduce` 平均時間 | 56.04 s | 18.42 s |
| `MPI_Waitall` 平均時間 | 59.06 s | 12.38 s |
| 双方向ノード間総転送量 | 289,023.6 MB | 105,093.1 MB |
| 平均DRAMアクセス帯域 | 20.66 GB/s | 29.98 GB/s |
| DRAM帯域律速の割合 | 14.20% | 46.80% |
| 倍精度ベクトル化率 | 23.55% | 20.20% |

APSの診断結果は、240ランク実行におけるアプリケーションが「MPI通信律速」に陥っていることを明確に示した。全ランク合計の関数呼び出し統計は以下の通りである。

- `MPI_Allreduce`: 約2億1,060万回
- `MPI_Waitall`: 約1億8,930万回
- `MPI_Isend`: 約22億2,000万回
- 2ノード間の総データ転送量: 289 GB

これに対し、120ランク構成では1対1通信（point-to-point）の呼び出し回数がほぼ半減し、ノード間通信量は約64%削減された。MPIに費やされる総時間はそれ以上の比率で大幅に減少した。MPI通信のボトルネックを解消した結果として、DRAMメモリアクセス帯域が二次的な制約要因として顕在化している。

120ランク構成における全ランク合計値は以下の通りである。

- `MPI_Allreduce`: 約9,600万回
- `MPI_Waitall`: 約9,960万回
- `MPI_Isend`: 約11億3,000万回
- 2ノード間の総データ転送量: 105 GB

なお、ランク0の挙動は全体の典型例ではない。240ランクのAPSプロファイルにおいて、ランク0のMPI時間比率は約51%にとどまっていたのに対し、他の大半のランクでは全時間の約83〜87%がMPI通信待ちに費やされていた。したがって、ランク0はOpenFOAM本体の計算ホットスポットをVTuneで特定するためのターゲットとして適しているが、通信オーバーヘッドや負荷不均衡の実態を把握するには全ランクの統計を俯瞰する必要がある。

APSの解析ログには、ノードごとの統計情報が一部欠落している旨の警告が出力されていた（240ランク実行ではランク4および195、120ランク実行でも同様に2件の記録が欠落）。APSは通信コミュニケータの総サイズを正常に認識しており、上位の傾向分析の整合性も保たれているが、総呼び出し回数の数値はわずかに過小評価されている可能性がある点に留意する。

## VTuneによるホットスポット解析

チューニング後の構成において最も有益な知見を提供したプロファイルは実行 #132 である。これは、2ノード120ランク構成のランク0を対象としてIntel VTune Hotspots解析を実施したものである。

```text
~/openfoam-profile/30007051832-6265016/hotspots.<host>/
```

VTuneによって計測された選択ランク（ランク0）の経過時間は62.06秒、CPU時間は59.26秒であった。主要なホットスポット関数は以下の通りである。

| --- | --- | ---: | ---: |
| `PMPI_Allreduce` | Intel MPI | 11.36 s | 19.2% |
| `PMPI_Waitall` | Intel MPI | 5.57 s | 9.4% |
| `Foam::GaussSeidelSmoother::smooth` | `libOpenFOAM` | 3.54 s | 6.0% |
| `ucp_worker_progress` | UCX | 2.84 s | 4.8% |
| `internal_Isend` | Intel MPI | 2.25 s | 3.8% |
| `cellLimitedGrad<...>::calcGrad` | `libfiniteVolume` | 1.40 s | 2.4% |
| `Foam::lduMatrix::residual` | `libOpenFOAM` | 1.11 s | 1.9% |
| `Foam::lduMatrix::Amul` | `libOpenFOAM` | 0.89 s | 1.5% |
| `linearUpwindV<...>::correction` | `libfiniteVolume` | 0.78 s | 1.3% |
| `Foam::fv::gaussGrad<double>::gradf` | `libfiniteVolume` | 0.75 s | 1.3% |

240ランク構成のランク0ではMPIの占有割合がさらに高く、`PMPI_Allreduce` が21.9%、`PMPI_Waitall` が11.3%、`internal_Isend` が8.3%を占めていた。ランク数を120へ適正化したことでこれら3つの通信オーバーヘッドがいずれも低下し、結果として行列平滑化（GaussSeidel）や空間勾配計算（grad）といったOpenFOAM本来の計算関数の比重が相対的に高まった。

HPC Characterization解析の結果もAPSと同様に、倍精度浮動小数点演算のSIMDベクトル化率が約20〜23%と低い水準にとどまることを示している。ただし、浮動小数点命令はCPUが実行する全マイクロオペレーション（uOps）の比較的小さな割合に過ぎず、また240ランクの実行構成はメモリ帯域の上限に達していなかった。したがって、ソースコードレベルのベクトル化を最優先の改善対象とするべきではない。一方、120ランク構成ではAPSが示す通りDRAMアクセス帯域の負荷が増加しており、MPI通信を削減した次の段階ではメモリアクセスの局所性（キャッシュ効率）が支配的なボトルネックとなる可能性が高い。

## 実行時パラメータ調整のガイドライン

1. 1ノード実行に限定する場合は、120 MPIランクを指定した上で `I_MPI_FABRICS=shm` を明示的に設定する。指定を省略した場合、Intel MPI 2021.15は不要なオーバーヘッドを伴う `mlx` プロバイダを選択してしまう。なお、ノード数制約がない場合は2ノード120ランク構成のほうがさらに高速であったが、1ノード条件の運用スコープ外である。
2. 複数回の測定において明確かつ安定した性能差が確認されない限り、Intel MPI既定のプロセス配置（ピニング）を使用する。`scatter` による短縮効果は約1秒にとどまり、`bunch` は明らかに性能が悪化した。
3. OpenFOAMの辞書設定 `topoControl=0` を維持する。Intel MPI自身がクラスタの物理トポロジーを考慮した効率的な集合通信アルゴリズムを備えており、OpenFOAM側の階層型縮約処理を強制するとかえって性能が低下した。
4. `nPollProcInterfaces=0` を維持する。`-1` を指定して完了済みインターフェースの即時ポーリングを有効化すると、本課題では約9%の性能悪化を招いた。
5. Intel MPIの集合通信自動チューニング（`I_MPI_TUNING_MODE=auto`）は、最適なランク数を確定した後にのみ検証する。通信過多であった240ランク配置では約2秒改善したものの、適正化済みの120ランク配置では56秒から58秒へと悪化した。またチューニングファイルは実行構成に強く依存するため、ノード数、ノードあたりランク数、通信ファブリック、MPIバージョンが同一である場合のみ再利用可能である。
6. 新たな計算ケースを扱う際は、まず「1ランクあたりのセル数」を基準にランク数の候補を絞り込み、APSを用いてMPI通信時間および負荷不均衡を定量化する。その上で、APSによって計算時間が最大と特定された代表ランクに対してVTuneを実行して詳細解析を行う。
7. VTuneの完全な解析結果は、プロファイル計測の完了後に自宅サーバーがクラスタから直接回収する。圧縮アーカイブの整合性を検証して自宅側へ確定保存した後に限りクラスタ上の元データを削除し、検証済みのテキストサマリーやCSVデータを成果物ツリーおよびメトリクス基盤へ公開する。
8. 将来的にソースコード改変が許可された場合、Gauss-Seidel平滑化、リミッター付き勾配計算、`lduMatrix` の残差計算および行列ベクトル積、ならびに超高頻度の大域リダクション処理を重点的な調査対象とする。現行の作業においては、これらの基本アルゴリズムは改変しない。

Intel MPIおよびVTuneの関連機能については、以下の公式ドキュメントを参照のこと。

## プロファイル機能の実装設計

現在のワークフローでは、共通の `OpenFOAM` ワークフローを単一のエントリポイントとし、プッシュ時は `[profile]` タグ、手動実行時は `profile` 入力パラメータにより通常計測からプロファイル計測へ切り替える。プロファイル実行はソースコードやビルド成果物を改変せず、実行プロトコルで指定された単一のMPIランクに対して一定時間（60秒間等）のみIntel VTuneの収集プロセスをアタッチする。プロファイル条件の変更は個別のコミットとして追跡する。単一ランクのサンプリング結果のみから全ランクの通信特性を安易に結論付けてはならない。

VTuneの完全な解析結果は `RUN_DIR/large-output/vtune` に一時生成され、`home-lab` ランナーが既存のクラスタ接続ラッパーを介して直接回収する。自宅サーバー側で解凍可能性、サイズ、SHA-256ハッシュを検証し、Actions実行の固定成果物ディレクトリ配下へ確定配置した後に限り、クラスタ側の `RUN_DIR` 全体を削除する。ParaView用データは通常のprofile Actionsでは生成せず、必要時にケースキャッシュまたはケースアーカイブから用意する。検証済みレポート、収集ステータス、JSON形式の構造化ファクト、およびサマリーテーブルは、プロファイル成果物および `experiment-metrics` の記録として保持する。VTune実行バイナリの識別情報およびバージョンは、プロビジョニング検証ログにより一元管理される。
